## 已修复的问题

### P2：订单查询持续分配临时对象

完成三个教学订单后，`CurrentOrder` 每次访问都会生成新订单；鱼箱视图和选鱼排序也反复分配。HUD 每帧多处查询这些属性。

修复：按订单序号缓存当前订单，复用只读鱼箱视图，以有界扫描替代临时列表和排序闭包。交付后自动更换缓存，保留最低价优先、ID 排序打破平局及部分预留的原有行为。

同一 .NET Release 回归中，预热后 **1,000 组订单/鱼箱查询：760,000 B → 0 B**。有鱼货的查询也验证为零分配。该数字只覆盖这些纯逻辑查询，**不代表整个 HUD 零分配，也不代表已测得帧率提升**。

### P2：订单体重要求与显示值不一致

飞梭鱼大鱼订单实际门槛为 1,745 g，但旧文案只显示“≥1.7 kg”。两位小数的鱼获显示也可能掩盖一克之差。

修复：普通鱼的体重显示保留至克的必要精度，订单要求与实际判定一致；例如 1.744 kg 和 1.745 kg 不再显示成同一个重量。存档格式、价值及门槛本身不变。

### P2：三鱼种订单让交易台文字重叠

旧布局中，第三条升级效果占逻辑 Y=688–708，底部提示占 Y=696–716，发生重叠。紧凑订单卡还把鱼名、数量、稀有/体重要求塞在同一行。

修复：鱼名与要求分成两行；交易台、图鉴侧栏按内容调整高度。共享布局数据供实际绘制和运行回归使用，覆盖 1/2/3 行订单。新三行交易台中，最后升级说明为 Y=724–744，底部提示为 Y=762–782。

## 建议下一步按此顺序推进

1. **先做完整 HUD 人工验收**：1280×720、1366×768 和宽屏下查看三行委托、装备满级、鱼箱已满、捕获提示；确认交易/暂停/图鉴按钮不会误触抛竿。
2. **减少钓鱼时的界面干扰**：优先突出咬钩、跃水放线、抄网时机，其余信息默认收起；再做实际用户测试，而非继续堆功能。
3. **统一美术和反馈**：收敛水面高光与道具材质，强化鱼在水中的轮廓；为传说鱼制作明确的放生动作，而不只依赖文字。
4. **单独推进真正的 VR 适配**：当前 manifest 的 XR 声明仅为 `com.unity.modules.xr`；已有 XR 判断/世界仪表不等于加载器、双目、控制器交互或舒适性已验收。后续用独立 PR 接入目标设备，再验证交互、转向、文本距离与 GPU/CPU 帧时间。
