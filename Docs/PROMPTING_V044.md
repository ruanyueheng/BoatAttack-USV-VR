## (a) 案例要点

### 1. 《小王子：星辰之旅》（Sac @Saccc_c，littleprince.dev）

### 2. Claude + Blender MCP + Unity 做 3D 游戏（Riza Sghari，Medium）
- Opus 通过 MCP 在运行中的 Blender 里执行 Python 建低模森林，烘焙后导入 Unity，再写玩法、打包。
- 核心是**闭环自验**：执行 → 渲染/截图 → 模型自己看图 → 决定改不改。Unity 那边也一样：写编辑器脚本 → 执行 → 读 Console → 截 Scene 视图。
- [链接](https://medium.com/@developer.rizasghari/how-i-used-claude-to-model-in-blender-and-build-a-3d-unity-game-25914ffee262)

### 3. Claude Code 游戏开发综述（chierhu，Medium）
- Claude 能验证“对不对”，验证不了“好不好玩、手感、视觉品质”，这几项必须由人验收。
- CLAUDE.md 要写清架构、命名，以及**“不要做什么”**；再配上引擎相关的 skill，加一个能“看见运行中游戏”的 MCP。
- 反例：有人让 AI 全包一个 Godot RTS，最后整个弃掉。原因是没有人把关，范围也失控。
- [链接](https://chierhu.medium.com/claude-code-for-game-development-7a88fcd19992)

### 4. Blender MCP 资产管线（best-games.io / claude-blender）
- 循环：资产简报 → Blender 白模 → **四视图检查** → 导出 → 试玩 → 返修。
- “场景数据能证明拱门宽 2 米，只有截图能看出它站在玩家旁边显得太窄。”
- [best-games.io](https://best-games.io/blog/codex-claude-code-blender-mcp-game-development-guide)、[claude-blender（自带 /blender-iterate 视觉反馈）](https://github.com/minihellboy/claude-blender)、[StraySpark CLAUDE.md 示例](https://www.strayspark.studio/blog/claude-code-game-developers-setup-guide)

### 共同规律
1. 小步：一个场景/一个功能一轮，不说“把游戏做好看”。
2. 先写风格和约束（风格圣经、禁止事项），再写需求。
3. 每一步都有**可截图、可量化**的验收标准，模型自己看图回看，最后由人确认“好不好看、好不好玩”。
4. AI 3D 生成只出毛坯，Blender 负责减面、修 UV、统一材质和比例。

```
目标：<一句话，玩家视角>

完成标准（全部满足才算完成）：
  1. <可量化项，例如“站在桌边 0.8m 内按扳机能拿起水壶”>
  2. 截图：<机位/视角> 存 Logs/V044/<名字>.png，先自己看图对照标准，再交给我
  3. 跑 Tools/Run-UnityValidation.ps1 <专项> 通过

```

### 模板 2：美术资产
```
资产：<名字>，用途 <在哪、离玩家多远>
参考：Logs/V044/ref/<图>；风格见 STYLE_BIBLE
预算：≤<N> 三角面，贴图 ≤1024，URP Simple Lit，单材质
流程：Tripo/混元出毛坯 → Blender 减面、修 UV、按真实尺寸缩放（单位 m） → 四视图渲染到 Logs/V044/art/<名字>_4view.png → 进场景截图（和玩家身高对比）
验收：比例真实（<尺寸>）；轮廓在 3m 外可辨认；与相邻资产色调一致

### 模板 3：玩法设计（先设计后实现）
```
先不要写代码。为 <玩法> 出 2–3 个方案，每个方案说明：玩家每 30 秒在做什么、目标/失败条件、需要的资产清单与面数预算、VR 交互方式、实现工作量。推荐其中一个并说明理由，等我选定后再实现。
```

### 模板 4：审查/回归
```
以挑剔玩家的身份审查 <场景>：按清单逐项截图（穿模、肢体扭曲、卡住、丑模型、UI 可读性），每个问题给出截图路径、严重程度、修复建议。只报告，不改代码。

## (c) 自问自答（v0.44）

**Q1 “模型美化”具体指什么？哪些模型、改到什么程度？**
A：以 `Logs/V044/sheet*.png` 的联系表为准，每个模型打 A/B/C 分，C 级必须重做、B 级可选。验收：重做后的四视图和进场景截图都放进 `Logs/V044/art/`；三角面数在预算内（道具 ≤3k，角色 ≤15k，建筑 ≤10k）；单位为米，和 1.7m 玩家放在一起比例正确。

**Q2 小王子绘本风怎么跟海岸渔村主题结合？**
A：只借**语言**，不借内容。配色把深夜蓝换成海军夜蓝，保留奶油白衬线字；“金色星芒”改成灯塔光、渔火的金色点缀；水彩纸纹改成旧航海图、渔网纸纹；图标用贝壳、鱼、锚、绳结。验收：UI 截图里不出现星球、玫瑰、狐狸等小王子元素；同时让 3 个人看截图，都能认出是“海边渔村”。

**Q3 UI 在 VR 里看得清吗？**
A：用世界空间面板，距离 0.8–1.5m，字体高度 ≥ 视角 1°（约 1.5–2.5cm），正文对比度 ≥4.5:1；避免细衬线小字号，正文改用较粗字重，衬线体只用在标题。验收：PICO 实机截图上 1m 外正文清晰可读。

**Q4 四岛秘境“更复杂有趣”怎么衡量？**
A：每座岛有一个独特机制（例如潮汐开路、灯塔反光解谜、捕捞特定鱼当钥匙、搭桥），一次流程 3–5 分钟，有明确的目标提示和奖励，四岛串成一条主线。验收：先出设计文档让用户选方案；实现后录一遍完整流程，不看提示能否通关、有没有卡关点。

**Q5 “交互真实、无穿模”的标准是什么？**
A：手和物体接触时手不陷进物体（误差 ≤2cm）；拿取范围以手或身体到物体的距离判断（≤0.8m），不要求碰撞体重合（水壶问题的根因就是这个）；第一人称靠墙低头不穿墙。验收：用专项测试脚本断言距离，再在 5 个典型位置各截一张图。

**Q6 “行走不卡”怎么验？**
A：CharacterController 的 stepOffset、slopeLimit 和地形碰撞要匹配；小台阶、门槛、码头木板缝都必须能走过去。验收：自动化脚本让角色沿预设路径走完全岛，统计速度低于阈值超过 0.5 秒的位置并输出清单，结果必须是 0。

**Q7 PICO 4 Ultra 性能预算是多少？**
A：72Hz 下每帧 ≤13.9ms；可见三角面 ≤30 万，Draw Call ≤150；贴图 ASTC，≤1024（主角 2048）；粒子每个系统 ≤200，避免大面积透明叠加；不加全局后处理。验收：实机或 Profiler 截图存档，每加一批资产记录一次。

**Q8 我（用户）应该提前说清楚的事**
- 截止日期，以及老师最看重什么（演示效果、玩法还是技术）。
- 哪些可以砍：优先级排序，P0 必须有、P2 可以不做。
- 每一项“完成”由谁来判定：模型自评 → 截图 → 用户点头。
- 哪些文件、系统不能动。

## (d) 工作流改进建议
1. **建 `Docs/STYLE_BIBLE.md`（风格圣经）**：色板 hex 值、字体、UI 组件样式、材质规则、参考图、禁用元素。所有美术和 UI 提示词都引用它。
2. **资产预算表**：每类资产的面数、贴图和材质上限，写进风格圣经，生成时强制执行。
3. **每项功能都要截图验收**：固定机位截图存进 `Logs/V044/`，做完放一张前后对比；模型先自己看图，再交给用户。
4. **设计和实现分两轮**：玩法类需求先出方案、让用户选，然后才写代码（模板 3）。
5. **一次只做一项**：PLAN 里的条目逐项勾选，每项一个提交，便于回滚。
6. **并行用子代理**：调研、资产生成、审查这类互相独立的工作交给子代理并行；同时只能有一个 Unity 实例（看 `Temp/UnityLockfile`），所以碰 Unity 的任务要串行。
7. **AI 3D 只当毛坯**：Tripo、混元出来的模型必须经过 Blender 减面、修 UV、统一比例这道流水线（脚本放在 `Tools/Art/build_v044_*.py`）。
8. **人的验收不可替代**：好不好玩、好不好看、晕不晕，每个里程碑都要戴上 PICO 实机看一次。
